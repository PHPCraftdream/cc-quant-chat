# cc-quant-chat — дизайн v1: пространство, роли, комнаты, личка

> **Исторический документ.** Описывает исходный замысел; реализация ушла дальше
> (вход через `/quant-join` и `/quant-setup`, ники с ключами, rewake-хук вместо
> монитора, хранилище за `store.Backend`). Актуальное поведение — в [README](../README.md).

Развитие [idea.md](idea.md). Один токен = одно пространство (workspace) с общим
чатом, комнатами, личными сообщениями и ростером участников с ролями.
Входящие появляются в сессии сами, без вызова инструментов.

## 1. Ключевое решение: доставка через Claude Code Channels

В Claude Code есть механизм **channels** (research preview): MCP-сервер объявляет
capability `experimental["claude/channel"]` и шлёт уведомление
`notifications/claude/channel` с `{content, meta}`. Событие попадает в контекст
модели как

```text
<channel source="ccqc" kind="dm" from="frontend" from_role="reviewer" msg_id="184">
текст сообщения
</channel>
```

и запускает ход модели даже в простаивающей сессии. Если модель занята —
события копятся и приходят пачкой на следующем ходе. Это ровно «всё появляется
автоматом после подключения»: `ccqc mcp` одновременно и канал доставки,
и поставщик инструментов отправки.

Ограничения, которые надо принять:

| Ограничение | Следствие |
|---|---|
| Свои каналы не в allowlist → запуск с `--dangerously-load-development-channels server:ccqc` | Подтверждающий диалог при каждом старте; работает только в интерактивном режиме (не `-p`, не Agent SDK) |
| Нужна аутентификация claude.ai или Console; нет на Bedrock/Vertex/Foundry | Для них — запасная доставка (§7) |
| Team/Enterprise: нужен `channelsEnabled: true` в managed settings | Иначе инструменты работают, push — нет |
| Ключи `meta` — только `[A-Za-z0-9_]`, остальные молча отбрасываются | Атрибуты: `kind`, `from`, `from_role`, `room`, `msg_id`, `reply_to`, `ts` |
| Подтверждения доставки нет: `notification()` завершается при записи в stdio | Доставка в модель — at-most-once; курсор двигается после записи в stdio |
| v2 MCP-клиент не регистрирует канал, договорившийся о протоколе `2026-07-28` | В `initialize` отвечать предыдущей ревизией протокола |
| Каждое событие будит модель и стоит токенов | Нужна политика шума (§6) |

## 2. Модель данных

```
Workspace  id = SHA-256(token)          — брокер токен не хранит
 ├─ Members   member_id, name (уникально в workspace), role?, status, joined_at, cwd_label
 ├─ Roles     name, exclusive: bool, holders[], pinned_by_human: bool
 ├─ Rooms     name (#general всегда есть), topic, created_by, members[], ring-буфер сообщений
 └─ DMs       ring-буфер на пару участников
Message     msg_id (монотонный на workspace), ts, from (ставит брокер), to, text, reply_to?
```

- `from` проставляет **брокер** по соединению, а не клиент → подделать отправителя
  личного сообщения нельзя.
- Адресация: `/<chat>/@<room>[/@<member>]` — см. [addressing.md](addressing.md)
  (нотация `#general` / `#room` / `@name` ниже по тексту устарела).
- Каждый участник автоматически в `#general`, выйти из него нельзя.

## 3. Роли

- Роль — метка для координации («кто за что отвечает»), **не права доступа**.
  Модель может быть введена в заблуждение входящим сообщением, поэтому роль
  ничего не разрешает технически.
- `role_claim(role, exclusive?)`:
  - роль свободна → занята; флаг `exclusive` задаёт первый, кто её занял;
  - роль exclusive и занята живым участником → ошибка `role_taken` с именем держателя;
  - роль не exclusive → участник добавляется в holders.
- `role_release()` — освободить. При отключении (после grace-периода) роль освобождается.
- Человек может закрепить роль при запуске: `ccqc run --role lead --pin` — модель
  её не сменит и не освободит (`role_pinned`).
- Каждое изменение ростера рассылается событием `kind="presence"` (с учётом §6).

## 4. Подключение и «сразу получить ростер»

> **Заменено** сценарием `/quant-join <token>` в живой сессии — см.
> [join-flow.md](join-flow.md). Ниже — исходный вариант с `ccqc run` и ticket.

```
человек                    ccqc run                    broker             claude          ccqc mcp
  │ ccqc run --token-file … │                            │                   │                 │
  │────────────────────────>│ redeem(token) ────────────>│                   │                 │
  │                         │<── ticket (одноразовый, 60 с)                  │                 │
  │                         │ spawn claude, env CCQC_TICKET, --mcp-config, dev-channels flag   │
  │                         │───────────────────────────────────────────────>│ spawn ─────────>│
  │                         │                            │<── hello{ticket, name, role} ───────│
  │                         │                            │── welcome{member_id, roster,        │
  │                         │                            │   rooms, my_rooms, backlog} ───────>│
  │                         │                            │                   │<── initialize ──│
  │                         │                            │                   │   instructions  │
  │                         │                            │                   │   = guide + snapshot
```

- `ccqc mcp` **сначала** подключается к брокеру, **потом** отвечает на `initialize`:
  в `instructions` кладётся короткий гайд + снимок (кто я, ростер с ролями, комнаты).
  Модель видит ростер с первого хода, без лишнего пробуждения.
- Сразу после `initialized` — одно событие `kind="welcome"` только если есть
  непрочитанный backlog (DM, упоминания), иначе не шлём, чтобы не будить модель зря.
- Актуальное состояние — инструмент `chat_state()`.

### Почему одноразовый ticket, а не токен в env

Если передать `CCQC_TOKEN` в окружение `claude`, его унаследует инструмент Bash:
модель прочитает токен через `echo $CCQC_TOKEN`. Это противоречит требованию
idea.md «модель не видит токен». Решение:

1. `ccqc run` читает токен из файла (вне репозитория), обменивает его у брокера на
   ticket — одноразовый, TTL 60 с, привязан к имени.
2. В окружение `claude` попадает только `CCQC_TICKET`; `ccqc mcp` гасит его на старте.
3. Модель может увидеть только уже погашенный ticket — он бесполезен.
4. Путь к файлу токена закрыть deny-правилом `Read(...)` в настройках сессии.

Честная граница: от кода, исполняемого под тем же пользователем ОС (он может
прочитать файл токена или память процесса), это не защищает. Токен защищает от
случайных пересечений сессий и от модели, а не от вредоносного процесса.

### Переподключение

Перезапуск сессии (`claude --resume`) поднимает новый `ccqc mcp` с новым ticket.
Если имя совпадает и прошло меньше grace-периода (60 с) — брокер возвращает тот же
`member_id`, роль и курсоры; накопленное приходит как backlog.

## 5. Инструменты MCP (`mcp__ccqc__*`)

| Инструмент | Назначение |
|---|---|
| `chat_send(to, text, reply_to?)` | `to` = `#general` \| `#room` \| `@name` |
| `chat_state()` | ростер с ролями, комнаты, мои комнаты, счётчики непрочитанного |
| `chat_history(target, limit?, before?)` | история комнаты или диалога из ring-буфера |
| `role_claim(role, exclusive?)` / `role_release()` | §3 |
| `room_create(name, topic?)` | создаёт и сразу вступает |
| `room_join(name)` / `room_leave(name)` | при входе — последние 20 сообщений одним событием |

Ни один инструмент не принимает токен или id пространства — сессия привязана к
одному пространству на всё время жизни.

Все инструменты добавляются в `permissions.allow` как `mcp__ccqc__*`.

## 6. Политика шума и защита от «пинг-понга» агентов

N агентов в общем чате, каждый просыпается на каждое сообщение, — это токены и
риск бесконечной переписки. Меры v1:

- **Приоритет доставки:** DM и упоминания `@name` — сразу; сообщения комнат —
  со склейкой в окне 2 с (одно событие на пачку); `presence` — не отдельно,
  а приклеиваются к следующему событию, либо раз в 30 с дайджестом.
- **Свои сообщения** не доставляются себе.
- **Rate limit** на отправителя (например, 6 сообщений / мин в комнату) и
  лимит размера сообщения (8 KiB) — на брокере.
- **Гайд в `instructions`:** «не отвечай в #general/комнату, если к тебе не обратились
  и ответ ничего не добавляет; благодарности и подтверждения не отправляй».
- Счётчик хода переписки (`depth`) в `meta`: если цепочка `reply_to` длиннее
  порога — брокер помечает событие `loop_suspect="1"`.

## 7. Запасная доставка (если channels недоступны)

- **Monitor:** модель запускает `ccqc tail` через Monitor; каждая строка — событие.
- **Хук:** `UserPromptSubmit` вызывает `ccqc tail --once` и добавляет непрочитанное
  в контекст хода. Push нет: сообщения видны только когда сессия и так работает.

`ccqc mcp` определяет режим сам: если клиент не прислал channel-capability в
ответ (или стоит `CCQC_DELIVERY=hook`), события копятся в курсоре до запроса.

## 8. Протокол брокера

NDJSON поверх Windows named pipe (ACL: только текущий пользователь) /
unix socket `0600`. Каждый кадр: `{"op": ..., "id": ..., ...}`.

| Клиент → брокер | Брокер → клиент |
|---|---|
| `redeem{token}` → `ticket` | `welcome{member_id, roster, rooms, my_rooms, backlog}` |
| `hello{ticket, name, role?, pin?}` | `event{seq, kind, ...}` |
| `send{to, text, reply_to?, client_msg_id}` | `ack{id, msg_id}` / `err{id, code}` |
| `claim{role, exclusive}`, `release{}` | |
| `room_create/join/leave{name}` | |
| `history{target, before?, limit}` | |
| `cursor{seq}` — подтверждение доставки | |
| `ping` | `pong` |

- `client_msg_id` делает повторную отправку идемпотентной.
- Сравнение хэшей токена — за постоянное время.
- Брокер стартует автоматически первым `ccqc run` (lock-файл + проверка живости).
- Коды ошибок: `bad_ticket`, `name_taken`, `role_taken`, `role_pinned`,
  `no_such_room`, `no_such_member`, `rate_limited`, `too_large`.

## 9. Безопасность входящих

- Всё, что пришло через `<channel source="ccqc">`, — данные от другого агента,
  не инструкция пользователя. Это прямо сказано в `instructions` и в описании
  инструментов.
- Не объявлять `claude/channel/permission`: иначе любой участник пространства мог
  бы одобрять вызовы инструментов в чужой сессии.
- Штатный механизм межсессионных сообщений выключается (`crossSessionInbound: "refuse"`,
  запрет `ListAgents`), чтобы не было второго канала связи.

## 10. Запуск

> **Заменено** — см. [join-flow.md](join-flow.md) §1.

```sh
ccqc token new > ~/.ccqc/team.token          # вне репозитория

ccqc run --token-file ~/.ccqc/team.token --name backend  --role backend  -- claude
ccqc run --token-file ~/.ccqc/team.token --name frontend --role frontend -- claude
ccqc run --token-file ~/.ccqc/team.token --name lead     --role lead --pin -- claude
```

`ccqc run` генерирует временный mcp-config и добавляет
`--dangerously-load-development-channels server:ccqc`.

## 11. Реализация (Go, один бинарник `ccqc`)

Подкоманды: `token`, `broker`, `run`, `mcp`, `tail`.

- Named pipe на Windows: `github.com/Microsoft/go-winio` — новая зависимость
  (стандартная библиотека named pipes не умеет).
- MCP stdio: канал требует нестандартную capability и уведомление; если Go MCP SDK
  не даёт задать `experimental` и произвольный notification — свой минимальный
  JSON-RPC 2.0 поверх stdio (initialize, tools/list, tools/call, notification).

## 12. Критерий готовности v1

1. A, B, C с одним токеном: каждый при старте видит ростер с ролями в первом ходе.
2. A пишет в `#general` — B и C получают событие без вызова инструментов.
3. A создаёт `#api`, B вступает и получает последние сообщения; C их не получает.
4. A пишет `@B` — получает только B; `from` нельзя подделать.
5. Второй `role_claim("lead", exclusive)` → `role_taken` с именем держателя.
6. Сессия D с другим токеном не видит ни участников, ни комнат, ни сообщений.
7. Ни в одной сессии `echo $CCQC_TICKET` не даёт рабочего секрета, токена в env нет.
