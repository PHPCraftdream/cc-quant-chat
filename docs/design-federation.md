# Объединение брокеров: синхронизация чатов и управление доверием

Проект следующего этапа — после развёртывания владельца, доски и документов
([design-owner-status-board.md](design-owner-status-board.md)). Цель: чат, который ведут
несколько брокеров на разных машинах, с общей историей, доской и документами. Вредный
узел не должен мочь подделывать, стирать или повышать себе права, а его вклад должен
отключаться и откатываться одной командой.

Вне объёма первой версии: автоматический поиск узлов, обход NAT, ретрансляторы,
шифрование содержимого от самих участников объединения, мосты в мессенджеры.

## 1. Три ключа

| Ключ | Что означает | Где лежит | Пароль |
|---|---|---|---|
| узла | «этот брокер»; `origin` = первые 16 байт SHA-256 открытого ключа | `<CCQC_HOME>/broker.key` | нет: брокер стартует сам |
| владельца | «этот человек»; права и администрирование | `<CCQC_HOME>/owner.key` | с консоли |
| участника | «этот агент»; авторство событий | `<CCQC_HOME>/nick-keys.json` | нет |

Ключ участника сейчас — общий секрет с брокером. Он заменяется парой Ed25519: брокер
хранит открытый ключ ника, участник подписывает им свои события.

## 2. Событие

Единица хранения и обмена. Сообщение, запись журнала доски, комментарий, версия документа,
вход ника, операция администратора — всё это события одного вида:

```
origin    узел, принявший событие от автора
seq       номер в журнале этого узла для этого чата (1, 2, 3, ...)
prev      хэш предыдущего события того же (origin, чат)
lamport   логические часы чата
kind      msg | board.* | doc.* | nick.* | admin.*
payload   содержимое (канонический JSON)
author    открытый ключ автора (участника или владельца)
sig       подпись автора над (chat_id, kind, payload, lamport)
node_sig  подпись узла над (origin, seq, prev, хэш остального)
```

- Подпись автора делает событие неподделываемым при пересылке через любые узлы.
- Цепочка `prev` на каждый `(origin, чат)` не даёт узлу вырезать или переписать своё
  прошлое: два разных события с одним `(origin, seq)` — доказательство обмана, такой узел
  автоматически переводится в карантин (§5).
- Таблица `events` — единственный источник истины. `messages`, `board_tasks`,
  `board_sprints`, `docs` становятся проекциями, которые пересобираются из неё. Тест на
  пересборку состояния доски из журнала уже заложен.

## 3. Обмен

Два брокера соединяются напрямую: TLS 1.3 (`crypto/tls`) с самоподписанными сертификатами
Ed25519, каждая сторона сверяет открытый ключ собеседника с ожидаемым `origin`. Адрес и
`origin` соседа задаёт человек: `ccqc peer add <адрес> <origin>` (операция администратора).

На каждый общий чат:

1. Стороны обмениваются вектором `{origin: наибольший seq}`.
2. Каждая досылает недостающие события, по источникам, по порядку `seq`. Пересылаются и
   события третьих узлов — подписи позволяют проверять их без доверия к пересылающему.
3. Принимающий проверяет подписи, цепочку и права автора (§4), затем применяет событие к
   проекциям. Непрошедшее проверку событие не сохраняется; причина — в журнале узла.

Курсор прочитанного участника становится вектором по источникам.

## 4. Слияние

- **Сообщения:** объединение множеств; порядок показа — `(lamport, origin, seq)`. Короткий
  номер `#184` остаётся локальным номером показа на каждом брокере; в ответах и ссылках
  между узлами используется `(origin, seq)`.
- **Доска:** состояние — свёртка событий в порядке `(lamport, origin)`; при одновременной
  правке одного поля побеждает большее. Номер задачи становится `T-<origin4>-<n>`, чтобы
  счётчики узлов не сталкивались; локальные задачи сохраняют короткую запись. Откат —
  обычное событие. Недопустимый по процессу переход, получившийся при слиянии, не
  отклоняется (история уже есть у других), а помечается в журнале для роли-менеджера.
- **Документы:** версия ссылается на родительскую. Две версии с одним родителем — конфликт:
  обе сохраняются, страница помечается, выбирает человек или агент новой версией.
- **Часы:** событие с `lamport`, превышающим известный максимум больше чем на 1000,
  отклоняется — узел не может «занять будущее», чтобы выигрывать все слияния.

## 5. Доверие

Уровень назначает владелец локального брокера для каждого узла-соседа и каждого чата;
по умолчанию низший.

| Уровень | Что принимается от узла |
|---|---|
| `read` | ничего; узел только получает события |
| `member` | сообщения и комментарии |
| `trusted` | также изменения доски и документов |

- **Допуск:** знания токена чата недостаточно. Узел входит в объединение чата по
  приглашению, подписанному владельцем принимающего брокера (`ccqc peer invite <чат>
  <origin> <уровень>`); приглашение — событие `admin.peer`.
- **Решение владельца (этап 4): узлы не соединяются по одному адресу.** Первое рукопожатие идёт по
  одноразовым данным, переданным сторонним каналом. `ccqc peer add <адрес> <origin>` этапа 3
  остаётся внутренним примитивом (тесты, отладка), единственный пользовательский путь —
  приглашение (все шаги — операции администратора, пароль владельца с консоли):
  1. Узел A: `ccqc peer invite <чат> [--ttl 15m]` печатает одну строку: адрес(а) A, полный
     открытый ключ узла A, одноразовый секрет (32 байта), срок. В node.db — только хэш секрета,
     срок, чат, счётчик попыток. Токена чата в приглашении нет.
  2. Владелец A передаёт строку владельцу B своим каналом (мессенджер, голос).
  3. Узел B: `ccqc peer accept <приглашение>` соединяется с A, TLS закреплён на ключ A из
     приглашения; B доказывает знание секрета, не раскрывая его: HMAC секретом над привязкой к
     этому TLS-соединению (экспортёр ключей TLS) и обоими ключами узлов. A проверяет хэш, срок,
     что не использовано; секрет гасится атомарно; три неверные попытки — приглашение сгорает.
  4. После рукопожатия узел в состоянии `pending`: ему ничего не передаётся, от него ничего не
     принимается. Обе стороны показывают короткий код сверки (6 цифр из обоих ключей узлов и
     секрета). `peer accept` на B спрашивает в консоли, совпадает ли код; на A владелец выполняет
     `ccqc peer confirm <origin> <код>`. Только после обоих подтверждений узел становится соседом,
     чат — общим, и A по установленному каналу передаёт B токен чата (чтобы агенты B вошли в чат у
     себя). Неподтверждённый `pending` истекает вместе с приглашением.
  5. Слушающий порт принимает TLS только от ключей уже известных соседей или от соединения с
     действующим приглашением; остальное рвётся до любых данных чата; лимиты рукопожатий — на ключ
     узла и на приглашение, с общим потолком на слушающий порт; на адрес собеседника ничего не
     привязывается (через туннель все входящие приходят с 127.0.0.1).
  6. Каждое приглашение, попытка, подтверждение и отказ — в `admin_log` и громким событием в чат.

  Код сверки нужен против перехвата приглашения в стороннем канале: перехвативший может встать
  посередине (принять приглашение у A как свой узел и представиться A перед B), тогда коды у A и
  B не совпадут.
- **Требование этапа 4: источники, которых мы не добавляли.** На этапе 3 узел принимает события
  чужого источника транзитивно (его ключ берётся из пачки, если хэшируется в origin) без решения
  владельца: сосед-`trusted` может ввести в общий чат сколько угодно выдуманных источников. На
  этапе 4: событие источника, не являющегося нашим соседом, принимается только через соседа
  уровня `trusted`, получает уровень не выше `member`, учитывается в лимитах того соседа, который
  его привёл; число неизвестных источников на соседа ограничено.
- **Права не переносятся.** Маркер `OWNER` и закреплённые роли действуют, только если
  подписаны ключом владельца, которому доверяет локальный брокер. Владелец чужого узла
  показывается как участник с пометкой источника.
- **Лимиты на источник** проверяет принимающий: сообщений и изменений в минуту, размер.
- **Пометка источника:** сообщения с других узлов показываются агентам с `origin`; будить
  агентов событиями чужого узла можно только с уровня `member` и выше.
- **Карантин:** `ccqc peer block <origin>` — события узла перестают приниматься и
  пересылаться. Автоматически — при обнаруженной развилке цепочки.
- **Откат вклада:** `ccqc peer revert <origin> --since <время>` — одним действием
  порождает события отката для всех изменений доски и документов, пришедших от узла с
  указанного момента, и скрывает его сообщения. Это тоже события, они расходятся по
  объединению и обратимы.

Что вредный узел всё же может: читать чаты, в которые допущен; слать события в пределах
лимитов своего уровня; пытаться убеждать агентов текстом. Чего не может: подделать
авторство, стереть или изменить чужое, получить права владельца или роли, незаметно
переписать собственную историю.

## 6. Этапы

1. **Ключи участников и подпись событий.** Пара Ed25519 на ник; существующие ники
   перепривязываются при следующем входе по старому секрету. Подпись автора хранится с
   сообщением, записью журнала доски, комментарием, версией документа; брокер проверяет.
2. **Единый журнал событий.** Таблица `events` с цепочкой и подписью узла; нынешние
   таблицы — проекции с пересборкой; перенос существующих данных миграцией.
3. **Обмен между двумя брокерами.** `ccqc peer add|list|remove`, TLS с закреплением
   ключей, векторный обмен, проверка и применение, правила слияния.
4. **Доверие.** Уровни, приглашения, лимиты на источник, карантин, откат вклада, пометка
   источника для агентов.

Каждый этап — отдельные коммиты с тестами и зелёным CI; этапы 1 и 2 ничего не меняют для
одиночного брокера и разворачиваются по отдельности.

## 7. Нерешённое

- Транспорт дальше прямого соединения (Yggdrasil встраивается в Go; iroh — Rust): решать
  после этапа 3, по опыту.
- Смена ключа чата при исключении узла и шифрование содержимого от ретрансляторов.
- Объём: журнал растёт бесконечно; нужна ли обрезка с контрольными точками.

## 8. Этап 1: как сделано

- Подписывается `ccqc/v1/event`, chat id, `origin` брокера, вид (`msg`, операция доски вроде
  `task.create`, `doc.put`), канонический JSON запроса без полей `sig`, `lamport`, `origin`, и
  значение `lamport`. Номера, выданные брокером при создании (T-n, #id, vN), не подписаны: их покроет
  `node_sig` этапа 2. Запрос с чужим `origin` — `wrong_origin`.
- `lamport` берётся у брокера (`clock`) и должен быть ровно «следующим» значением часов чата;
  иначе `stale_clock` с текущим значением в данных ошибки (клиент подписывает заново, до 5 раз).
  Событие, занявшее несколько строк (`doc.move` — две версии), делит одно значение и одну подпись.
- В строках `messages`, `board_log`, `board_comments`, `doc_versions` хранятся `author_pub`, `sig`
  и подписанный `payload` (у комментария он в строке журнала). Это ровно поля строки `events`
  этапа 2.
- Ник — Ed25519; join = challenge + подпись; старый ник перепривязывается один раз по старому
  секрету; после этого join только по секрету отказывается. Клиенты proto < 4 без ключа
  принимаются, их события — без подписи, в состоянии они помечены `unsigned`.
- `ccqc owner say` подписывает ключом владельца (author_pub = ключ владельца): метка OWNER
  проверяема по самой строке. Каноническая форма — `json.Marshal` Go (экранирует `<`, `>`, `&`);
  для узлов на других языках её нужно зафиксировать до этапа 3.

## 9. Этап 2: как сделано

- `events`: PK `(chat_id, origin, seq)`; `prev` = ID предыдущего события (sha256 от origin, seq,
  prev и хэша остальных полей); `node_sig` — подпись `broker.key` над теми же данными. Код —
  `internal/events`; таблица — миграция 0010; запись — `sqlite.appendEvent` в той же транзакции,
  что и проекция. Интерфейс `store.Backend` (Append/Load) не менялся; `BoardTx`/`DocsTx`
  получили `RecordEvent`.
- Проекции пишет единая `applyEvent` (сообщения, ники, комнаты, настройки); доска и документы
  исполняют свою логику, а событие хранит образы затронутых строк (`assigned.rows`) — пересборка
  записывает образы обратно и не исполняет правила заново (у старых строк нет запроса, только
  эффект). `payload` — подписанный канон запроса; `assigned` — всё, что выдал узел.
- Не события: курсор `seen`, строка `chats`, `admin_log`, настройки уровня брокера. Подпись
  автора у админ-событий (роль, настройка, сброс ника) пока пустая: нонс админ-подписи не
  сохраняется; это этап 4.
- `lamport` служебных событий = текущий счётчик чата без увеличения; порядок — `(lamport, origin,
  seq)`.
- Пересборка — через временную БД: проигрыш событий, сравнение таблиц `EXCEPT` в обе стороны,
  подмена в одной транзакции. Перенос старых строк — при старте брокера после `initNode`
  (SQL подписать не может): по чату одна транзакция и отметка в `meta`.

## 10. Этап 3a: обмен журналами — как сделано

- Журнал v2 (`meta.journal_version = 2`): `Rest()` — sha256 от (chat, lamport, kind, ts, H(payload),
  H(author_pub), H(sig), H(assigned)). Событие можно отдать «закрытым» (`Redact`): четыре содержимых
  заменяются хэшами, `ID()` и `node_sig` остаются проверяемыми, цепочка origin не рвётся. Хэш секрета
  ника и курсор `seen` — состояние узла, из `nick.*` убраны; при открытии чата собственные события
  v1 пересобираются (prev, node_sig) и помечаются версией (до обмена этого никто не видел).
- Что уходит открытым: сообщения комнат, `task.*`/`sprint.*`/`board.*`/`doc.*`, `room.*`,
  `nick.register|key|reset` (имя и ключ). Закрытым: `msg` в `@direct`, `config.set`, `nick.pin`,
  `import.*`, неизвестные виды. Личные сообщения между узлами не поддерживаются (§7).
- `internal/peer`: TLS 1.3 + самоподписанный Ed25519-сертификат из `broker.key`; обе стороны
  проверяют, что ключ сертификата даёт ожидаемый origin (`VerifyPeerCertificate`). Кадры —
  JSON-строки `hello` (origin, общие чаты), `vector` ({origin: max seq} по чату), `events`
  (пачка в порядке (lamport, origin, seq) с ключами origin'ов), `bye`. Две стороны, набравшие друг
  друга, оставляют одну сессию (инициатор с меньшим origin). Новые локальные события — через
  `OnEvents` сразу; обрыв — переподключение с растущей паузой до 30 с и добор по вектору.
- Приём: `check` (форма заголовка, флаг узла, `node_sig` по ключу origin — ключ чужого origin
  принимается, только если хэшируется в него, подпись автора, lamport не выше известного + 1000 и не
  меньше предыдущего события origin) и `accept` (цепочка `prev`, занесение по `(origin, seq)`);
  отвергнутое не хранится, причина — в лог, обмен идёт дальше. Два разных события с одним
  `(origin, seq)` — развилка: origin помечается (`flagged_origins`), сессия закрывается.
- Узел-админ: `ccqc peer add|list|remove|share|unshare` (подписи владельца), таблицы node.db
  `peers` (уровень доверия `trusted`), `peer_chats`; настройка `peer.listen` (по умолчанию пусто:
  брокер никого не принимает).
- База чата 0002: `events.ord` (порядок применения; пересборка проигрывает по `ord`), `hidden`,
  `remote_nicks`. Применение чужих событий к проекциям (глобальные ссылки `(origin, seq)`, LWW по
  `(lamport, origin)`, версии документов с родителями, правила операции↔образу, ник@origin4) —
  этап 3b.
- Ограничение: снимки `import.*` старых баз уходят закрытыми, доска и страницы чата, перенесённого из
  базы до журнала, на другой узел не попадают.
- Адрес соседа — URI со схемой: сейчас только `tcp://host:port` (голый `host:port` принимается как
  tcp и хранится как URI; другая схема — понятная ошибка), так носитель добавляется без смены
  формата. Идентичность соседа — только его ключ из TLS, не IP; `peer.listen` допускает loopback.
- Одно соединение в любом направлении достаточно: узел без `peer.listen` — полноценный сосед, если
  сам дозванивается. Узел, до которого дозвонились, не набирает уже соединённого соседа, а
  недоступный адрес (за NAT) заносит в лог один раз за серию неудач, с растущей паузой до 30 с.
  Правило «из двух сессий остаётся одна» (меньший origin инициатора) не касается единственной.
  Сессия шлёт `ping` раз в 20 с и рвётся при тишине 75 с: мёртвая половина соединения не мешает
  новой.
- Отвергнутое событие не просят снова в петле: сессия помнит отказ, в vector объявляет по этому
  origin «всё есть» (сосед не шлёт ни его, ни следующих), пишет в лог один раз и спрашивает вновь
  через паузу 5 с, удваивая до 5 мин; три отказа подряд на собственных событиях соседа — сессия
  закрывается, диалер ждёт от 1 до 10 минут. Слушающий порт: не больше 32 одновременных
  незавершённых рукопожатий (остальные закрываются сразу) и 64 сессий.

## 11. Этап 3b-1: сообщения, ники, комнаты — как сделано

- `AcceptEvent` кладёт событие и применяет его к проекциям в одной транзакции (`applyRemote`,
  `internal/store/sqlite/remote.go`); событие, не прошедшее правила применения, не сохраняется.
  Пересборка идёт по `ord`: свои события — через `applyEvent`, чужие (`events.remote = 1`) — через
  `applyRemote`; номера, выданные узлом принятому, получаются теми же.
- Глобальное имя того, что создало событие, — `(origin, seq)` этого события (`entity_refs`); номер
  `#id` — локальный. Ссылка на сообщение (`reply_to`) в подписанном запросе — номер автора, поэтому
  событие несёт ещё `assigned.reply_ref {o, s}`; получатель переводит его в свой номер (нет такого —
  0).
- Участник другого узла — `ник@origin4` (первые четыре символа origin). Ссылка в чужом событии на
  свой ник (`ник@<наш origin4>`) снова становится голым именем. Сообщение с подписью проверяется по
  ключу, который его узел записал для ника (`remote_nicks`); без подписи — под гарантией узла
  (в состоянии `unsigned`); метка OWNER чужого узла не переносится.
- Комната, названная раньше своего создания (сообщение или вход пришли от другого источника),
  создаётся заглушкой с наибольшей меткой; настоящее `room.create` её заменяет. Из двух созданий
  одной комнаты побеждает меньшее `(lamport, origin)` — порядок прихода не важен.
- Брокер принимает событие под замком чата (`acceptRemote`): память и живые участники получают
  его, как собственное сообщение; адресат `@комната/@ник@origin4` получает `to_me`.
- `@direct` на ник другого узла — ошибка `remote_member`.
- Порядок показа — порядок применения на узле (локальный номер); `(lamport, origin)` лежат в
  строке сообщения. Доска и документы чужих узлов в журнал попадают, в проекции — на этапах 3b-2/3.

## 12. Этап 3b-2: доска — как сделано

- Глобальное имя задачи, спринта, комментария и строки журнала доски — `(origin, seq)` события,
  которое её создало (`entity_refs`, там же `num` — номер, который ей дал создатель). Событие
  доски несёт `assigned.refs`: глобальные имена всего, что его образы называют номером (задача,
  спринт в поле `sprint`, `carried`, `reverts`, комментарий); у того, что событие создаёт, имени
  ещё нет. Получатель переводит имена в свои номера до любой записи; неизвестное имя при событии,
  которое мы держим закрытым или не смогли применить, — событие остаётся в журнале без применения;
  имя, чьё событие ещё не пришло, — отказ с повтором (`errMissingRef`).
- Поле задачи/спринта/комментария/процесса — last-writer-wins по `(lamport, origin)`
  (`board_stamps`): при одновременной правке одного поля у всех узлов остаётся одно значение,
  чужие поля остаются своим авторам. `updated_at` — максимум. Свои события ставят метки при записи
  (`noteBoard`), пересборка — тем же кодом.
- Проверка заявленного: вид события задаёт сущность записи журнала, допустимые поля `after`,
  таблицы образов, число создаваемых строк; поля запроса, подписанного автором (`title`, `status`,
  `priority`, `sprint`, `name`, `goal`...), должны совпасть с записью журнала. Непрошедшее — не
  сохраняется.
- Индекс «один активный спринт» снят: два узла могут запустить по спринту, слияние не отвергает
  то, что уже есть в истории.
- Исполнители (`assignee`, `created_by`, `actor`, автор комментария) — `ник@origin4`.
- Не сделано в 3b-2: показ `T-<origin4>-<n>` (задача чужого узла показывается под номером этого
  узла, создатель и его номер лежат в `entity_refs`), разбор такой ссылки, пометка недопустимых
  по процессу переходов для менеджера, уведомления исполнителю о чужих изменениях.
