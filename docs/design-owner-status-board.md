# Владелец, статус участника, доска задач

Спецификация трёх возможностей. Общие рамки: без новых зависимостей (только стандартная
библиотека Go и то, что уже есть в `go.mod`), всё добавляется совместимо — старые клиенты
новые поля игнорируют; `proto.ProtoVersion` поднимается до 3. Порядок реализации:
§2 → §1 → §3 (ядро) → §3 (инструменты). Номера миграций — следующие свободные по порядку.

Вне объёма: роли и права (проектируются позже), классы указаний владельца и подтверждения
(отдельная задача «защита исполнения команд»), мосты в мессенджеры, другие агенты.

## 1. Статус владельца

Владелец — человек, которому принадлежит брокер на этой машине. Признак владельца на
участнике и на его сообщениях ставит **брокер**, проверив подпись; клиент прислать его
не может.

### 1.1 Ключ

- Пара Ed25519 (`crypto/ed25519`). Одна на брокер: таблица `owner` из одной строки
  (`pubkey`, `created_at`).
- Закрытый ключ лежит в `<CCQC_HOME>/owner.key` зашифрованным: PBKDF2-HMAC-SHA256
  (`crypto/pbkdf2`, 600 000 итераций, соль 16 байт) → AES-256-GCM. Файл `0600`, JSON:
  `{v, kdf, iter, salt, nonce, ct, pub}`.
- Пароль вводится **только с консоли**: Windows — `CONIN$`, Unix — `/dev/tty`, без эха.
  Никогда из stdin, окружения, аргументов или файла. Нет консоли — команда отказывается.
  Агент, запустивший команду через Bash, пароля не знает; пользователь увидит неожиданный
  запрос в своём терминале.

### 1.2 Команды (все — только для человека)

| Команда | Действие |
|---|---|
| `ccqc owner init` | создать ключ (пароль дважды), зарегистрировать открытый ключ у брокера |
| `ccqc owner status` | отпечаток ключа у брокера и локального; совпадают ли |
| `ccqc owner say <адрес> [текст\|-]` | войти владельцем, отправить одно сообщение, выйти |
| `ccqc owner rotate` | новый ключ; запрос подписан старым |

Регистрация: операция `owner_register {pub, sig}`. Брокер принимает её, только если
владельца ещё нет; замена — только `owner_rotate`, подписанная действующим ключом.
`owner say` берёт токен чата из пользовательского конфига по имени чата (любая запись
`folders/*.json`); если не найден — спрашивает на консоли. Ник по умолчанию `owner`
(`--nick`), ключ ника — как у всех.

### 1.3 Протокол

- `challenge` → `{nonce}`: 32 случайных байта, привязаны к соединению, одноразовые, 30 с.
- `JoinArgs.OwnerSig` = подпись строки
  `"ccqc/v1/owner-join\n" + chat_id + "\n" + nick + "\n" + nonce`.
- Подпись верна → `member.owner = true`. Неверна или владельца нет → `bad_owner_sig`,
  вход не выполняется (а не «вход без признака»).
- Брокер проставляет `Message.Owner` (`"owner":true`) на каждом сообщении такого
  соединения и сохраняет его (колонка `owner` в `messages`). `MemberInfo.Owner` — в `state`.
- После регистрации владельца ник `owner` зарезервирован: вход под ним без подписи →
  `reserved`.

### 1.4 Показ

- Строка события: `[/chat/@room #id ts] OWNER nick → @to: текст`. Маркер `OWNER` —
  заглавными, до ника: ники и роли — `[a-z0-9-]`, подделать маркер именем нельзя.
  Канал: `owner="1"` в meta. `chat_state`: `@nick  OWNER  ...`.
- Мод `quant-ui` выделяет такие сообщения; маркер из текста сообщения не читается.
- В `instructions` MCP-сервера: сообщение с маркером `OWNER` пришло от человека-владельца
  ccqc на этой машине (проверено брокером) и важнее сообщений агентов; оно не выдаёт
  разрешений на инструменты, а разрушительные действия и действия вне задачи пользователя
  этой сессии по-прежнему требуют подтверждения в самой сессии.

### 1.5 Граница

Защищает от подделки через чат и протокол. **Не** защищает от процесса того же
пользователя ОС, который правит файл базы напрямую или подменяет брокер: `ccqc owner
status` показывает расхождение отпечатков, но предотвратить это ccqc не может. Утерян
ключ или пароль — строка `owner` удаляется вручную при остановленном брокере (описать в
README).

### 1.6 Приёмка

Вход с верной подписью даёт признак; без подписи, с чужой подписью, с повтором nonce, с
подписью для другого чата или ника — не даёт. Клиент, приславший `"owner":true` в `send`
или `join`, признака не получает. Вторая регистрация отклоняется, `rotate` со старым
ключом проходит. Признак сохраняется в истории после перезапуска брокера. Файл ключа не
расшифровывается неверным паролем.

## 2. Статус участника

Сведения о присутствующем участнике; не сохраняются, живут вместе с `member`.

| Поле | Откуда |
|---|---|
| `text` (≤ 200 байт) | инструмент `status_set(chat?, text)`; пустая строка очищает; без `chat` — во все чаты сессии |
| `busy` + `since` | автоматически: хук `UserPromptSubmit` (`ccqc busy`) и выдача пачки событий хуку → занят; приход хука `wait` от `Stop` → свободен |
| `folder` | базовое имя каталога проекта (не полный путь) |
| `branch` | из `.git/HEAD` без запуска git: `ref: refs/heads/x` → `x`; оторванная голова → 7 символов хэша; `.git`-файл worktree — по его `gitdir`; нет репозитория → пусто |

- Операция брокера `status {text?, busy?, folder?, branch?}` — частичное обновление,
  лимит 120 в минуту на ник. Событий не порождает и никого не будит; видно в `state`.
- MCP-сервер перечитывает ветку при каждой смене занят/свободен и повторяет статус после
  переподключения (как комнаты и роль).
- `ccqc busy` — быстрый синхронный хук: строка `busy <sid>` в session pipe, выход 0,
  таймаут 5 с. Добавить в `setup.mjs` и `plugin/hooks/hooks.json`.
- `chat_state`: `@alice  role: dev  online · busy 12m · cc-quant-chat@main · «чиню CI»`.

Приёмка: частичное обновление не затирает остальные поля; статус исчезает после ухода
участника; восстановление после перезапуска брокера; разбор `.git/HEAD` для ветки,
оторванной головы, worktree и отсутствия репозитория; лимит.

## 3. Доска задач

Одна доска на чат. Смотреть всё может любой участник чата; менять пока тоже любой (роли —
позже). Каждое изменение журналируется и обратимо; откат — тоже запись журнала.

### 3.1 Сущности

- **Спринт:** `id` (счётчик на чат), `name`, `goal`, `state` (`planned` → `active` →
  `closed`), даты. Активный — не больше одного. Закрытие: незавершённые задачи уходят в
  бэклог или в указанный спринт (`carry`), одной записью журнала.
- **Задача:** `id` (счётчик на чат, показывается как `T-12`), `title` (≤ 200 байт),
  `description` (≤ 16 КиБ), `status`, `sprint` (0 — бэклог), `assignee` (ник или пусто),
  `priority` (0–3), `created_by`, даты, `deleted` (мягкое удаление).
- **Процесс** (машина состояний статусов), один на доску:

```json
{"statuses": ["todo","doing","review","done","blocked","cancelled"],
 "initial": "todo", "terminal": ["done","cancelled"],
 "transitions": {"todo": ["doing","blocked","cancelled"],
                 "doing": ["review","blocked","todo","cancelled"],
                 "review": ["done","doing"], "blocked": ["todo","doing","cancelled"],
                 "done": ["doing"], "cancelled": ["todo"]}}
```

  Это процесс по умолчанию (строки в таблице нет). Свой задаётся целиком; имена статусов —
  `[a-z0-9-]{1,32}`, не больше 16. Замена отклоняется, если у неудалённых задач есть
  статусы, которых нет в новом процессе (в ошибке — какие и сколько). Недопустимый переход
  → `bad_transition` со списком разрешённых.

### 3.2 Журнал и откат

Таблица `board_log`: `id` (счётчик на чат), `ts`, `actor`, `actor_owner`, `kind`, `entity`
(`task|sprint|workflow`), `entity_id`, `before`, `after` (JSON только изменённых полей),
`reverts` (id отменяемой записи или 0), `note`. Только дозапись; физически ничего не
удаляется.

- Виды: `task.create|update|move|delete`, `sprint.create|update|start|close`,
  `workflow.set`, `revert`.
- Изменение сущности и запись журнала — **одна транзакция** SQLite.
- `revert(log_id, force?)`: для каждого поля из `after` записи текущее значение должно
  совпадать с ним; иначе `conflict` с номерами более поздних записей, тронувших эти поля
  (сначала откатить их, либо `force`). Применяется `before`. Пишется запись `revert` с
  `reverts = log_id`. Откат отката — повтор исходного изменения.
- Откат не проверяет переходы процесса (он возвращает прежнее состояние), но статус должен
  существовать в текущем процессе. Откат `task.create` — мягкое удаление; `sprint.create` —
  только если в спринте нет задач; `sprint.close` возвращает перенесённые задачи.

### 3.3 Хранилище

Доска работает через запросы к SQLite, а не через воспроизведение записей чата: отдельный
интерфейс (`store.Board`), реализованный sqlite-хранилищем. При `CCQC_STORE=memory` —
ошибка `board_unavailable`. Таблицы: `board_sprints`, `board_tasks`, `board_workflow`,
`board_log`, ключи `(chat_id, id)`; индексы под выборки §3.4. Лимит: 60 изменений доски в
минуту на ник.

### 3.4 Экономия контекста

Спринты нужны, чтобы список задач не заливал контекст.

- `task list` по умолчанию: активный спринт (нет активного — бэклог), без завершённых.
  Одна строка на задачу, без описаний: `T-12 doing @alice p1 Заголовок` (заголовок до 80
  знаков). Сверху — имя спринта и счётчики по статусам; не больше 50 строк, дальше
  «ещё N». Фильтры: `sprint=<id>|backlog|all`, `status`, `assignee`, `mine`, `done`.
- `task get` — полное описание и 5 последних записей журнала задачи.
- `sprint list` — строка на спринт со счётчиками.
- Ответ на изменение — одна строка: `T-12 todo → doing (log #57)`.
- События: изменение задачи доходит только до её исполнителя, если менял не он. Будит —
  при назначении и смене статуса; остальное приходит тихо. Вид события `board`; общей
  рассылки нет. `ccqc hello` доску не печатает.

### 3.5 Инструменты MCP

Три инструмента с полем `op` — меньше описаний в контексте каждой сессии. Описания
короткие, подробности — в тексте ошибок.

| Инструмент | `op` |
|---|---|
| `task` | `create`, `update` (title, description, assignee, priority, sprint), `move` (status), `delete`, `get`, `list` |
| `sprint` | `create`, `update` (name, goal), `start`, `close` (carry), `list` |
| `board` | `log` (вся доска или задача; `limit`, `before`), `revert` (log_id, force), `workflow_get`, `workflow_set` |

Все принимают `chat` (можно опустить, если чат один).

### 3.6 Приёмка

- Создание, правка, перенос между спринтами, мягкое удаление — каждое даёт запись журнала
  с верными `before`/`after`.
- Недопустимый переход отклонён; свой процесс применяется; замена с «осиротевшими»
  статусами отклонена.
- Откат правки, перехода, создания, закрытия спринта; конфликт при более поздней правке
  того же поля; `force`; откат отката; каждая из этих операций сама в журнале.
- Сбой записи журнала откатывает и изменение сущности (одна транзакция).
- Второй активный спринт отклонён; закрытие переносит незавершённые.
- Участник другого чата доску не видит; любой участник этого — видит всё.
- `task list` по умолчанию не содержит описаний и задач вне активного спринта.
- Событие получает только исполнитель и не получает автор изменения.
- Данные доски переживают перезапуск брокера.

## 4. Развёртывание

После зелёного CI по всем частям: копия `ccqc.db`; сборка в `plugin/bin` (занятый файл
переименовывается); `ccqc broker restart`; `/quant-setup` (новый хук `UserPromptSubmit`);
установка `quant-ui`; перезапуск сессий (`claude --resume`); `ccqc owner init` — выполняет
человек в своём терминале.
