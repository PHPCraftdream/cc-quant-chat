# Защита ключей ников: план (протокол 6)

Задача main-expert #103 по решению владельца. Требование: **ни данных брокера, ни данных клиента по
отдельности не должно хватать, чтобы войти под ником**. Пароль на каждую сессию не подходит; новых
зависимостей без обоснования нет. Это шаг 1: только проект, код — после согласования. Продолжение
[design-invites.md](design-invites.md) (вход по приглашению) и README, раздел «Nick keys and signed events».

## 1. Исходное состояние

- Ник = пара Ed25519. Закрытый ключ (seed) лежит открытым текстом в `nick-keys.json` (папка `CCQC_HOME`,
  запись `<chat id>/<nick>/ed25519`), рядом — старый секрет ника (`<chat id>/<nick>`, для proto ≤3).
  Брокер хранит только открытый ключ (`nicks.pubkey` в БД чата). Вход — `challenge`, затем `join` с `pub` и
  `nick_sig` (подпись над `chat id`, ник, `pub`, nonce соединения); события подписаны этим же ключом, у
  каждой строки журнала свой `author_pub`.
- Данных брокера для входа **уже** не хватает. Не хватает защиты клиента: файл `nick-keys.json` (и его копия
  в `backup-*`, которые лежат рядом с `node.db` в `CCQC_HOME`) целиком открывает все ники машины.
- Сессия Claude Code = процесс `ccqc mcp`; ключ держит только он (хуки ходят через сессионный пайп и ключа не
  видят). Свой ключ держат ещё терминальные команды: `ccqc doc` (ник `cli`, до сих пор proto 3: вход по
  секрету, события без подписи) и `ccqc owner say` / админ-операции (ключ владельца под паролем — отдельная
  защита, не меняется).

## 2. Схема

Два секрета по 32 случайных байта, у каждого своя сторона; ключ подписи получается из обоих.

- **A** — секрет клиента (одна машина — один A). Хранилище ОС (п. 4). В `nick-keys.json` закрытых ключей
  больше нет.
- **B** — секрет брокера, **свой на каждую пару (чат, ник)**, случайный, только в `node.db` (п. 5).
- Производные (HKDF-SHA256, `crypto/hkdf` из стандартной библиотеки Go ≥1.24; A и B — полноценная
  энтропия, растягивать пароль не нужно). `chat` — 64-hex id чата, `0x00` — разделитель (в нике его не бывает):
  - `auth_seed = HKDF(ikm = A, salt = "ccqc/auth/v1", info = chat ‖ 0x00 ‖ nick)` → ключ **auth** (Ed25519);
  - `sign_seed = HKDF(ikm = A ‖ B, salt = "ccqc/nick-key/v1", info = chat ‖ 0x00 ‖ nick)` → ключ ника.
- Открытый ключ ника **в чате не меняется по виду**: `nicks.pubkey`, `author_pub`, подписи событий,
  `checkAuthor`, федерация — как сейчас. Меняется только то, откуда клиент берёт закрытый ключ. Целиком он
  нигде не лежит: живёт в памяти процесса сессии (там же и сейчас — `chatConn.priv`).
- Брокер хранит **открытый** auth-ключ, B и `sign_pub` (для сверки с БД чата). A у брокера не бывает ни в каком
  виде.

Что получается. Только `node.db` (копия, бэкап, утечка): B, открытые ключи — ключа подписи не собрать, A
неподбираем. Только данные клиента: A — без B ключа нет. Нужны оба.

### Замечания к наброску

1. **auth — на пару (чат, ник), а не один на A.** Иначе открытый auth-ключ связывает ники и чаты в `node.db`.
   Ключ подписи и так свой на чат (п. 6 наброска): различают B и `info`.
2. **«Выдача B после доказательства A» нужно ещё и принудить на входе.** Одной выдачи мало: тот, у кого есть A и
   B (из `node.db`), выведет ключ и войдёт `join`-ом, минуя выдачу — без проверки сессии и без громкого события.
   Поэтому брокер принимает `join` ника с защищённым ключом **только на соединении, где прошёл `key_unlock`**.
3. **Курица и яйцо при первой регистрации.** Приглашение подписывает `pub`, а `pub` выводится из B, который
   должен выдать брокер. Решение — шаг `key_prepare`: брокер кладёт случайный B в память соединения (на диск —
   только вместе с успешным входом), клиент выводит ключи и входит с приглашением. Не вошёл — B пропал.
4. **Запись в двух БД** (ключ ника — БД чата, B — `node.db`): порядок «`pending` в `node.db` → запись ника →
   `active`»; при старте брокер сверяет `pending` с `nicks.pubkey` (совпало — `active`, нет — удалить).
5. **Что даёт B на одной машине, честно.** Брокер обычно на той же машине, что и клиент; снимок диска целиком
   содержит и A, и `node.db`. Прибавка от B: (а) A, вышедший отдельно (файловый запасной вариант, чужая
   копия папки с клиентскими файлами), не открывает ник; (б) **отзыв на стороне брокера**: владелец удаляет B —
   ключ мёртв у всех копий A сразу; (в) каждый вход проходит через брокера и виден (учёт, лимиты, громкие
   события). Если же брокер на другом хосте/другом пользователе — прибавка полная. От копии папки на другую
   машину при работающем хранилище ОС защищает уже сам A (п. 4), B — второй рубеж.

## 3. Порядок входа (proto 6)

Клиент держит A (прочитал из хранилища один раз при старте процесса), выводит `auth_priv` и по нему — вход:

1. `challenge` → `nonce₁`.
2. `key_unlock {chat, nick, sid, auth_sig}`; `auth_sig = Sign(auth_priv, "ccqc/auth/v1/unlock" ‖ chat ‖ nick ‖
   nonce₁)` (поля с длиной, как `NickJoinMessage`). Брокер проверяет: запись есть, ник не онлайн, подпись, окно
   отказов (п. 7), `sid` (п. 8). Ответ: `{b}`. Ошибки: `unlock_denied` (подпись; считается), `unlock_session`
   (чужая сессия), `unlock_unknown` (ключ не защищён — клиент идёт путём п. 9), `rate_limited`.
3. Клиент: `sign_priv` из `A ‖ B`; `challenge` → `nonce₂`; **обычный `join` proto 5** (`pub`, `nick_sig`):
   `verifyNick` не меняется. Брокер дополнительно требует, чтобы это соединение уже прошло `key_unlock` для этой
   пары (флаг на соединении), иначе `key_not_unlocked`.
4. Дальше всё как сейчас: подписи событий, `stale_clock`, `author_pub`. После обрыва/рестарта брокера клиент
   повторяет 1–3 (A в памяти до конца процесса; после вывода ключей A затирается по возможности — в Go
   это best effort).

Брокер на `key_unlock` пишет в `admin_log` (`key.unlock`: ник, чат, 8 символов `sid`, pid и образ клиента — п. 8;
ничего секретного). В чат — громкая строка только при отказе по сессии и при перебое (п. 7), не на каждый вход.

## 4. Хранилище A на клиенте

Файл `keystore.json` в `CCQC_HOME` (не секрет): `{"v":1,"kind":"dpapi|keychain|secret-service|file"}`. Новых
Go-зависимостей **нет**; платформенные средства:

| ОС | Где лежит A | Как | Зависимость |
|---|---|---|---|
| Windows | файл `client-secret.dpapi` — блоб DPAPI (`CryptProtectData`, область — текущий пользователь, `CRYPTPROTECT_UI_FORBIDDEN`, энтропия — метка `ccqc/client-secret/v1`) | `golang.org/x/sys/windows` — **уже в go.mod** | нет новых |
| macOS | связка ключей: сервис `ccqc`, запись `client-secret-v1` | вызов `/usr/bin/security` (cgo и Security.framework — нет: проект собирается без cgo). `add-generic-password -w` принимает значение только в argv: оно видно `ps` того же пользователя на миллисекунды (класс угроз, который и так не закрыт, п. 10) | нет, системная утилита |
| Linux | Secret Service (libsecret): атрибуты `service=ccqc account=client-secret-v1` | `secret-tool store/lookup`, секрет идёт через stdin | пакет `libsecret-tools` на машине; не нужен для сборки |
| где хранилища нет (сервер без D-Bus и т.п.) | файл `client-secret.key`, режим 0600 | запасной вариант | — |

Запасной файл — **честно слабее**: A и `node.db` в одной папке, копия папки открывает ники. Клиент говорит об
этом громко: в ответе `chat_join`, в `ccqc keys status`, строкой при старте. Предлагается класть запасной файл
не в `CCQC_HOME`, а в другой каталог пользователя (открытый вопрос 2).

Порядок надёжности: A создаётся и **читается обратно** до первого обращения к брокеру; нельзя зарегистрировать
ключ, из которого A потом не восстановить. A потерян (переустановка ОС, перенос профиля) — все его ники
восстанавливаются новым приглашением, как сегодня при потере `nick-keys.json`; B без A бесполезен.

## 5. Хранилище B у брокера

Только `node.db` (миграция `0007_nick_secrets.sql`), **не** БД чата: БД чатов уходят в федерацию, в экспорт и
`ccqc db`; B за пределы узла выходить не должен (в тестах: B нет ни в одном кадре федерации, ни в `db verify`,
ни в дампе журнала).

```sql
CREATE TABLE nick_secrets (
  chat_id TEXT NOT NULL, nick TEXT NOT NULL,
  b BLOB NOT NULL,                 -- 32 случайных байта
  auth_pub BLOB NOT NULL,          -- Ed25519, из A
  sign_pub TEXT NOT NULL,          -- ключ, записанный в чате (сверка)
  sid_hash TEXT NOT NULL DEFAULT '',  -- SHA-256 id сессии; '' — терминальный ник без привязки
  state TEXT NOT NULL,             -- pending | active
  created_at INTEGER NOT NULL, unlocked_at INTEGER NOT NULL DEFAULT 0,
  fails INTEGER NOT NULL DEFAULT 0, fail_until INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (chat_id, nick));
```

Ник защищён, если есть строка `active` и её `sign_pub` равен `nicks.pubkey` чата. Приглашение с заменой ключа
(`ccqc invite` для существующего ника) удаляет старую строку и заводит новую; операция владельца
`ccqc key revoke <chat> <nick>` удаляет строку (подписана, в `admin_log`, громкая строка): ключ мёртв, ник
возвращается приглашением. Шифровать `node.db` на диске не предлагается: ключу негде лежать.

## 6. Ключ — свой на каждый чат

Уже следует из схемы: B случайный на (чат, ник), `info` содержит id чата и ник; один и тот же ник в двух чатах
даёт два несвязанных открытых ключа и два auth-ключа. Утечка пары (A, B) одного ника не открывает другие.

## 7. Защита от перебора и повтора

- Подпись Ed25519 не угадывается; всё же `fails` на пару: 5 неверных подряд → пауза `fail_until` 1 мин,
  удвоение до 1 ч, сбрасывается успехом; громкая строка в чат на 3-й неудаче (раз в час).
- Повтор: `nonce` одноразовый и привязан к соединению (`takeNonce`, `challengeTTL`); метки подписей разные для
  `unlock`, `join`, `move` (п. 9) — подпись одной операции не годится для другой.
- `key_prepare` — один раз на соединение и пару; брокер хранит ожидающий B только в памяти соединения.

## 8. Привязка к сессии

Брокер запоминает `sid` Claude Code, на котором ник зарегистрирован (приглашение погашено / перенос выполнен).
`key_unlock` с другим `sid` → `unlock_session`: отказ, нужно новое приглашение владельца (оно заменяет ключ и
привязку), в чат громкое событие «вход под @nick из другой сессии (abcd1234…) отклонён» (раз в час). Тот же
`sid` — `claude --resume`, рестарт процесса, обрыв брокера — входит как раньше.

**Что `sid` на самом деле.** Его сообщает клиент; ядро его не подтверждает. Он не секрет (лежит в
`folders/*.json`, в именах файлов транскриптов). Поэтому проверка `sid` — защита от **ошибки и от копии A в
чужой сессии**, но не граница против процесса того же пользователя, который знает и A (может прочитать хранилище),
и `sid`. Не обещаем большего.

**Что можно взять с именованного канала, и что из этого реально:**

| Признак | Как получить | Реально ли |
|---|---|---|
| PID клиента | Windows: `GetNamedPipeClientProcessId` на серверном конце (есть в `x/sys/windows`); Unix: `SO_PEERCRED` (Linux), `LOCAL_PEERPID` (macOS) | Подтверждено ядром, подделать нельзя. Но **привязка к PID ломает** `--resume` (новый процесс) — годится как запись в журнал, не как условие входа |
| Образ процесса, время создания | `QueryFullProcessImageName` + `GetProcessTimes` / `/proc/<pid>/exe`, `stat` | Для журнала и разбора случая. Другой процесс того же пользователя может запустить тот же `ccqc.exe` или его копию — как условие театр |
| Родитель = процесс Claude Code | Windows: снимок процессов; Linux: `/proc/<pid>/stat` | Родителя на Windows можно задать при создании процесса (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`); на Linux чужим потомком стать нельзя, но Bash-инструменты сессии — именно потомки Claude Code. Как условие — театр, как улика в журнале — полезно |
| Два живых клиента с одним `sid` | уже есть: `name_online` | Реально; остаётся |
| uid клиента | пайп с защитным дескриптором на пользователя, `verifyOwner` | Уже есть |

Предложение: условие входа — `sid`; ядерные PID/образ/время/родитель пишутся в `admin_log` и в громкое событие
при отказе (шаг 3 реализации, не граница защиты).

**Терминальные ники** (`ccqc doc`, ник `cli`): `sid` пуст, привязки нет (`sid_hash = ''`); защищены A и B как
остальные, вход на каждую команду (`key_unlock` — одна строка в `admin_log`).

## 9. Перенос существующих ключей

Цель: **без нового приглашения каждому**, сохранив историю ника (его `author_pub` у старых строк остаётся
прежним: они проверяются по собственному ключу строки).

Ник сдвигается на защищённый ключ **доказательством владения старым**: тем, кто и сегодня полностью им владеет.
Кадр `join` с `enroll {auth_pub, proof}`, где `proof` — одно из:

- `invite` — одноразовое приглашение (новый ник или замена; подпись приглашения теперь покрывает ещё и
  `auth_pub`: `proto.InviteSubject6`);
- `old_key` — подпись старым ключом `P` над `"ccqc/key-move/v1" ‖ chat ‖ nick ‖ P' ‖ auth_pub ‖ nonce`;
- `secret` — старый секрет ника (proto ≤3-ники, как сегодня `bindPub`).

Шаги клиента (порядок обязателен, переживает падение в любой точке): (1) создать A и прочитать обратно (п. 4);
(2) `challenge`, `key_prepare` → B; (3) вывести `P'`, `auth_pub`; (4) `join` с `enroll` и `nick_sig` ключом
`P'`; брокер: проверка `proof`, `pending` → запись `pub = P'` → `active`, громкая строка в чат «ключ @nick
переведён на защищённый»; (5) только после успеха клиент удаляет старые seed и секрет из `nick-keys.json`. Упал
между 4 и 5 — при следующем старте `key_unlock` проходит, клиент видит, что перенос завершён, и удаляет старое.

**Старые копии мертвы после переноса, а не после «удаления»:** на брокере `pub` ника заменён, и старый seed
больше ничей ключ не открывает. Затирать файлы на диске не требуется (на SSD и в бэкапах всё равно не
получилось бы). Поэтому копии `nick-keys.json` в `backup-*` после переноса безвредны. До переноса они живые, и
**кто перенесёт ник первым, тот им владеет**: если первым был посторонний, у настоящего клиента `old_key` не
сходится (`name_taken`/«ключ под другим ключом»), он поднимает тревогу, владелец делает `ccqc invite` (замена).
Отсюда команда `ccqc keys migrate` — перенести **все** ники машины сразу, не дожидаясь очередного входа, — и
рекомендация владельцу выполнить её первым делом; копии `backup-*` с `node.db` до переноса B не содержат,
после — содержат B без A.

Ник без локального seed (потерян) переносу не подлежит — только приглашение, как сегодня.

## 10. Терминальные участники

- **Ключ владельца** (`ccqc owner say`, админ-операции, `owner`): под паролем на консоли, как сейчас;
  схема A+B его не касается.
- **Ник `cli`** и другие терминальные ники: обычный защищённый ник без привязки к сессии. Сейчас `@cli`
  входит proto 3 по секрету, без подписей (`[unsigned: no signing key]`); при обязательной защите так входить
  нельзя. Предлагается: `ccqc invite <chat> cli` один раз, дальше `ccqc doc` входит сам (A из хранилища ОС,
  пароль не нужен). Вариант «`ccqc doc` от имени владельца с паролем на каждую команду» дороже в использовании
  (открытый вопрос 5).

## 11. Совместимость, версия протокола

`ProtoVersion = 6` (`proto.KeysProto`). Новые операции: `key_prepare`, `key_unlock`; новые поля `join`:
`enroll`, `sid`; новые коды: `key_not_unlocked`, `unlock_session`, `unlock_denied`, `unlock_unknown`,
`key_protected`.

| Клиент / брокер | Что происходит |
|---|---|
| proto 6 к брокеру ≤5 | `key_prepare` неизвестна → клиент остаётся на открытом seed как сегодня, A не создаёт, пишет «брокер старый, ключ не защищён» |
| proto ≤5 к брокеру 6, ник не переведён | входит как сейчас (окно совместимости) |
| proto ≤5 к брокеру 6, ник переведён | отказ `key_protected`: «ключ этого ника защищён: обновите ccqc» |
| proto 6 к брокеру 6, ник не переведён | перенос по п. 9 (автоматически при входе, если A создаётся) |

Окно закрывает владелец: настройка брокера `keys.require_protected` (по умолчанию выкл., как `peer.*`
подписанная админ-операция); включённая, отказывает клиентам proto ≤5 и никам, не переведённым на защиту
(нужны перенос или приглашение). Состояние видно: в `chat_state` у ника рядом с `[unsigned: …]` добавляется
`[key not protected]`; `ccqc keys status` показывает вид хранилища и по каждому нику «защищён / не защищён /
старый секрет». **Откат** на брокер ≤5: переведённые ники остаются на ключе `P'`, а его закрытая часть нигде не
хранится; старый клиент войти им не сможет, нужно приглашение (замена ключа). Поэтому окно совместимости
(`keys.require_protected` выключен) держится, пока владелец не убедится, что откат не понадобится.

## 12. Модель угроз

**Закрыто:**

- копия `nick-keys.json` и папок `backup-*` (после переноса — мёртвые ключи; до переноса — окно п. 9);
- копия `node.db` или всей `CCQC_HOME` на **другую** машину/профиль: A в DPAPI/связке/Secret Service там не
  расшифровывается (при запасном файле — нет, см. ниже);
- `node.db` отдельно (утечка бэкапа, федерационной БД, диска брокера): B и открытые ключи без A;
- данные клиента отдельно (в т.ч. A из запасного файла): без B ключа нет, брокер выдаёт B только по подписи
  auth-ключом, с проверкой сессии, учётом и громкой строкой при отказе;
- вход из чужой сессии с тем же A (ошибка, форк, копия): отказ, новое приглашение владельца;
- перебор и повтор подписей: п. 7;
- токен чата не открывает ник (при владельце `nick_reset` — подписанная операция владельца, уже сделано).

**Не закрыто — без приукрашивания:**

- **любой процесс того же пользователя ОС.** Он может читать память живой сессии (ключ целиком там), либо сам
  вызвать DPAPI / `security` / `secret-tool`, получить A, объявить нужный `sid` (он не секрет) и взять B у
  брокера. Инструменты агентов Claude Code (Bash и т.п.) запускаются от того же пользователя: внушённый
  агент в любой сессии — это именно такой процесс. Закрыть можно только секретом, который вводит человек
  (отклонено владельцем) или изоляцией ОС;
- **A и B вместе:** снимок диска целиком при запасном файле, живой взлом машины (это полный доступ);
- **запасной файл** без хранилища ОС (п. 4): копия папки открывает ники;
- пароль ключа владельца слабый → перебор файла офлайн (вне этого проекта; параметры KDF — в `internal/owner`);
- подменённый брокер того же пользователя: не получает A, но получает подписи auth-ключа (их без A не
  переиграть, nonce разный) и B своей БД; защита пайпа от чужого создателя уже есть (`verifyOwner`).

## 13. Сложность, проверки, порядок работ

Критерий приёмки (код, после утверждения): **тесты атак** — только `node.db` (+ все открытые данные) не даёт
входа; только клиентские файлы (A) не даёт входа; копия `nick-keys.json` до переноса работает один раз и
перестаёт после переноса; гонка переноса (двое с одним старым ключом — выигрывает один, второй видит отказ и
громкую строку); вход из другой сессии отказан и виден в чате; `join` без `key_unlock` отказан; падение между
шагами 4 и 5 переноса; брокер ≤5 с клиентом 6 и наоборот; B нигде не вышел за `node.db` (кадры федерации,
`db verify`, дамп); `pending` после падения сверяется при старте.

Порядок работ: **KEY-2** выводы ключей, хранилища ОС (Windows DPAPI, запасной файл; macOS/Linux через утилиты),
`keystore.json`, `ccqc keys status`; **KEY-3** брокер: `nick_secrets`, `key_prepare`/`key_unlock`, принуждение
на `join`, лимиты, учёт; **KEY-4** `sid` и привязка, громкие события, PID/образ в `admin_log`; **KEY-5**
перенос (`enroll`, `ccqc keys migrate`), приглашение с `auth_pub`, `ccqc doc` на защищённом нике; **KEY-6**
`keys.require_protected`, `key revoke`, README и этот документ как описание сделанного.

## 14. Открытые вопросы владельцу

1. **macOS/Linux:** достаточно ли системных утилит (`security`, `secret-tool`) и запасного файла с громким
   предупреждением, или на машине без хранилища ОС ccqc должен отказаться запускаться? (Рекомендация —
   предупреждать.) Нужен ли отдельный пакет Go с D-Bus для Linux (`godbus`, +1 зависимость) — рекомендуем нет.
2. **Где лежит запасной файл A:** в другом каталоге, чем `CCQC_HOME`, чтобы копия «папки ccqc» его не захватила?
3. **Привязка к сессии:** отказ (нужно новое приглашение) — как в наброске — или только оповещение? Что
   считать той же сессией при `/clear` и `--fork-session`: сегодня «после `/clear` сессия сохраняет чаты» —
   надо проверить, что `sid` стабилен, прежде чем делать привязку обязательной.
4. **Перенос:** автоматически при ближайшем входе (рекомендуется) плюс `ccqc keys migrate` сразу для всех? Когда
   включать `keys.require_protected` по умолчанию и закрывать окно proto ≤5?
5. **Терминальные ники (`cli`):** один раз приглашение и без пароля (рекомендуется) или команды от имени
   владельца с паролем на каждый вызов?
6. **Один A на пользователя или на чат?** Рекомендуется один: утечка A без B ничего не открывает, а утечка
   пары (A, B) открывает один ник.
7. **Смена B (ротация):** только вручную через `key revoke` + новое приглашение (меняет открытый ключ ника)?
8. **Принять границу п. 12:** процесс того же пользователя (в том числе инструмент внушённого агента) защитой
   не закрыт.
