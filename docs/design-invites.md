# Вход в чат только по приглашению

Решение владельца (передано main-expert, сообщение #69). Реализация — после этапа 3 и до этапа 4
федерации; здесь — что именно строится и чем проверяется. Знания токена чата перестаёт хватать для
входа, даже локально.

**KEY-7 (решение владельца, #129): совместимости нет.** Всё, что ниже говорит о старых чатах, токене, переходе и
`nick reset`, — история и убрано; действует раздел «KEY-7» в конце.

## Смысл

Одноразовое приглашение используется один раз: оно привязывает к нику открытый ключ. Дальше
участник входит ключом (challenge + подпись, как на этапе 1 федерации). Это и есть «сессионный
секрет, который ротируется»: каждый вход доказывается новой подписью, переиспользуемый секрет по
проводу не ходит. Отдельный bearer-токен сессии не вводится.

## Что строится

1. **Чат создаёт владелец:** `ccqc chat new <имя>` (операция администратора). `chat_id` случайный
   (32 байта), токена нет. `ccqc token new` убран (KEY-7).
2. **Приглашение:** `ccqc invite <chat> <nick> [--ttl 15m]` (администратор) печатает одну строку:
   `chat_id`, имя чата, ник, одноразовый секрет (32 байта), срок. В базе чата — хэш секрета, ник,
   срок, счётчик попыток. Приглашение именное: годится только для этого ника.
3. **Вход по приглашению:** `/quant-join <приглашение>`. MCP создаёт пару ключей ника; брокер
   проверяет секрет без раскрытия (HMAC секретом над nonce соединения и открытым ключом), привязывает
   ключ к нику, гасит приглашение атомарно; три неверные попытки — приглашение сгорает. Событие
   `nick.register` несёт хэш приглашения и того, кто его выдал (подпись владельца из admin-события).
4. **Повторные входы — только ключом.** Сессия помнит `chat_id` и ник; токен и приглашение нигде не
   хранятся (уходит и ограничение «токен лежит в конфиге и в контексте модели»: использованное
   приглашение бесполезно).
5. **Перепривязка:** приглашение на уже существующий ник заменяет `nick reset`: старый ключ перестаёт
   работать, в чат уходит громкое событие. `nick reset` убран (KEY-7).
6. **Переход (убран в KEY-7):** старые чаты (`id` = SHA-256 токена) входят по `chat_id`, как все; входа по токену и по
   секрету нет, клиенты proto < 6 отказаны.
7. **Один механизм** (хэш, срок, попытки, атомарное гашение, журнал, громкое событие) — общий с
   приглашением узла (design-federation §5, решение владельца этапа 4): один пакет.
8. **CLI-участники** (`ccqc doc ...`, `ccqc owner say`) входят ключом владельца или по своему
   приглашению. Пути входа по одному токену не остаётся. (Как именно — уточняется при реализации и
   записывается сюда.)

## Приёмка

- Отказ: вход без приглашения; с чужим ником; с просроченным; с использованным; после трёх неверных
  попыток.
- Параллельное использование одного приглашения двумя клиентами: проходит один.
- После входа приглашение есть в журнале (хэш, кто выдал), секрета нигде нет.
- Перепривязка отключает старый ключ.
- Старый чат входит по `chat_id`; старый клиент отказан (`old_client`).

## План реализации (до кода; на согласование с main-expert)

### 1. Один пакет приглашений `internal/invite`

Общий для входа в чат и для приглашения узла (design-federation §5, этап 4). Приглашение — **ключ
Ed25519 на один раз**: секрет (32 байта, seed) живёт только в строке приглашения; брокер хранит
его **открытый ключ** и хэш (id). Доказательство знания секрета — **подпись** этим ключом, а не HMAC:
HMAC требует, чтобы проверяющий держал тот же секрет (в базе лежал бы ключ проверки, равный
секрету), подпись не раскрывает ничего и не требует хранить секрет. Это отступление от слов «хэш
секрета + HMAC» из #69; смысл («в базе нет того, чем можно войти»; «доказательство без раскрытия»)
сохранён и усилен. Если нужен именно HMAC — скажите, но тогда в базе лежит производный ключ
проверки, и кража базы даёт вход по непогашенным приглашениям.

- Подпись над `"ccqc/invite/v1" ‖ привязка ‖ предмет`. Привязка — то, что делает подпись годной
  только на этом соединении: для входа в чат — nonce соединения (операция `challenge`, как у входа
  ключом); для узла — экспортёр TLS-соединения (`ConnectionState.ExportKeyingMaterial`). Предмет — что
  приглашение даёт: для чата `chat_id ‖ ник ‖ открытый ключ ника`; для узла — оба ключа узлов.
- Строка приглашения: `ccqc1.` + base64url(JSON `{v, kind: "chat"|"node", seed, exp, chat_id, chat,
  nick | addrs, key}`) + контрольная сумма (4 байта SHA-256): опечатка видна до сети. Токена чата в
  ней нет.
- Запись (`Record`): `id` (hex SHA-256 открытого ключа приглашения), `pub`, `kind`, `scope` (JSON:
  ник; для узла — чат), `expires_at`, `tries`, `state` (`open|used|burnt|revoked`), `issued_by`
  (ключ владельца), `issued_at`, `used_at`, `used_by` (ключ, который привязан). Интерфейс
  хранилища: `Issue`, `Lookup`, `Burn(id, now, used_by)` (атомарный `UPDATE … WHERE state='open'
  AND expires_at>? AND tries<3`, выигрывает один), `Fail(id)` (счётчик, на третьей — `burnt`).
- Реализации таблицы: `chats/<id>.db` (приглашения в чат), `node.db` (приглашения узла).

### 2. Таблицы и события

- `chats/<id>.db`, миграция 0005: `invites (id PK, pub, nick, expires_at, tries, state, issued_by,
  issued_at, used_at, used_by)`; `meta.mode` (убрано в KEY-7: все чаты входят
  по приглашению; id старого чата — SHA-256 токена, нового — случайный). Приглашения — состояние узла, не проекция журнала, но каждое действие — **событие**:
  `invite.issue` (admin-событие с подписью владельца, как `config.set`; содержит `id` и `pub`, не
  секрет), `invite.fail` / `invite.burn` / `invite.revoke` (громкая строка в чат, запись в
  `admin_log`). Эти виды экспортируются закрытыми (дело узла).
- `nick.register` / `nick.key` по приглашению несут `assigned.invite = {id, issued_by_seq}` —
  кем выдано (ссылка на admin-событие `invite.issue` с подписью владельца) и по какому. Секрета нет
  нигде: ни в базе, ни в журнале, ни в логе.

### 3. Операции администратора (подпись владельца, пароль с консоли)

- `ccqc chat new <имя>` → `chat_new`: 32 случайных байта = `chat_id`, чат создаётся пустым в режиме
  `invite`, токена нет. Без инициализированного владельца — отказ с подсказкой `ccqc owner init`.
  `ccqc token new` убран.
- `ccqc invite <chat> <nick> [--ttl 15m]` → `invite_new` (ttl 1 мин … 7 сут.): печатает строку.
  Приглашение на существующий ник = перепривязка ключа. `ccqc invite revoke <id>`, `ccqc invite
  list <chat>` (id, ник, срок, состояние; секрета нет).
- `chat_find` (подпись владельца): имя чата → `chat_id` для CLI-участников (токенов в конфиге нет).

### 4. Протокол входа (proto 5)

1. `challenge` → nonce (как сейчас).
2. `join{chat: <chat_id>, name, pub, nick_sig, invite: {id, sig}, proto: 5}` — для **нового или
   перепривязываемого** ника. `nick_sig` — как на этапе 1 (владение ключом ника); `invite.sig` —
   подпись ключом приглашения над `привязка=nonce`, `предмет = chat_id ‖ nick ‖ pub`.
3. Брокер: ищет приглашение по `id`; нет/просрочено/использовано/сожжено/ник не тот → отказ
   `invite_invalid` (один код на все случаи, без подсказок); подпись неверна → `Fail` (3 неверных —
   `burnt`); верна → в одной транзакции `Burn` + `nick.register|nick.key` + `invite.use`; ответ — как
   у обычного входа.
4. Повторные входы: `join{chat, name, pub, nick_sig}` без `invite` (challenge+подпись, этап 1).
   Токен нигде не участвует; поля `token` в `join` нет.
5. Лимит: неудачных попыток с одного соединения/источника — общий потолок (limits.go); неизвестный
   `id` счётчика не имеет, считается за соединением.
6. Параллельное использование одного приглашения двумя клиентами: `Burn` атомарен — проходит
   один, второй получает `invite_invalid`.

### 5. Переход (п.6 из #69; убран в KEY-7)

Старый чат входит по `chat_id`, как любой; токен, секрет ника и `nick_reset` убраны; без владельца чат не создаётся.

### 6. Что меняется у клиентов

- `/quant-join <приглашение>` (один аргумент; ник — внутри приглашения; навык и `chat_join`):
  MCP заводит защищённый ключ ника (design-keys.md), подписывает, входит, **запоминает
  `chat_id` + ник**, приглашение выбрасывает. `chat_join(invite)` — единственный вариант
  (`chat_join(token, name)` убран в KEY-7). Возобновление сессии: `key_unlock` и вход по `chat_id`.
  В контекст модели и конфиг токен больше не попадает (приглашение погашено и бесполезно).
- CLI-участники: `ccqc doc|role|config|owner say` входят **ключом владельца** (`OwnerSig` с паролем с
  консоли, ник `OWNER`), чат находят по имени через `chat_find`; токен не нужен и пути входа по
  одному токену не остаётся. Если CLI нужен другой ник — `ccqc <cmd> --invite <строка>`: тот же
  вход по приглашению, ключ ника — защищённый, как у любого ника.

### 7. Тесты приёмки

Отказ: без приглашения; с чужим ником; просроченное (часы подменяются); использованное; после трёх
неверных подписей (четвёртая — с верной подписью — тоже отказ, `burnt`); отозванное. Два клиента
одним приглашением одновременно — проходит один (`-race`). После входа: в журнале `invite.issue` +
`nick.register` с `assigned.invite`; секрета нет ни в базе, ни в журнале, ни в логе, ни в
`admin_log` (поиск по байтам seed в файлах после прогона). Перепривязка: старый ключ получает
`name_taken`/`bad_sig`, новый входит, громкая строка в чат. Клиент ниже proto 6 — `old_client`. Повторный вход ключом без приглашения; токена-входа нет. Приглашение узла (этап 4) — те же `Burn/Fail` на другой привязке.

### 8. Порядок работ и коммитов

1. `internal/invite` (формат, подпись/проверка, интерфейс, sqlite-реализация, тесты на атомарность).
2. Миграция 0005, `chat_new`/`invite_new`/`invite_revoke`/`invite_list`/`chat_find`, события.
3. Протокол входа (broker), proto 5, `chat_id` вместо токена, переход старых чатов.
4. Клиенты: MCP/навык `quant-join`, CLI (`chat new`, `invite`, вход CLI-участников ключом владельца).
5. Документация; `nick reset` и `token new` убраны в KEY-7.
Каждый шаг — свой коммит с локальным прогоном (gofmt, linelimit, vet, test, test -race) и CI.

## Как сделано (шаги 1–5)

- `internal/invite`: строка `ccqc1.<base64url JSON>.<контрольная сумма>`, поле `kind` (chat | node);
  приглашение — ключ Ed25519 на один раз, подпись над `метка ‖ привязка ‖ предмет`; `Redeem`
  погашает одним `UPDATE … WHERE state='open' AND expires_at>? AND tries<3`, любой отказ —
  `invite_invalid`, неверное доказательство — `BadProof` (счётчик, на третьем `burnt`).
  Отступление от «HMAC»: подпись (в базе только открытый ключ), согласовано main-expert.
- Хранилище: `chats/<id>.db` миграция 0005 (`invites`, `meta.mode`), события `invite.issue` /
  `invite.revoke` (подпись владельца), `invite.fail`, `nick.register` / `nick.key` с
  `assigned.invite`; при обмене между узлами все `invite.*` уходят закрытыми.
- Протокол: `join{chat, name, pub, nick_sig, invite{id, sig}}` (с proto 6 — ещё `enroll`, design-keys.md).
  Входа по токену нет (убран в KEY-7 вместе с `Broker.lenientEntry`, `SigningProto`, `InviteProto`).
- Клиенты: `/quant-join <приглашение>`, `chat_join(invite)`, вход по `chat_id` и ключу; CLI
  (`owner say`, `doc`, `role`, `config`, `peer`, `invite`) находят чат по имени у брокера, `doc` входит
  ключом владельца или `--invite`. Хранение ключей ника — design-keys.md (`nick-keys.json` убран).
- Приглашение узла (этап 4) — на том же пакете (`kind = node`, привязка — экспортёр TLS, код сверки).

## KEY-7: совместимости нет

Чат входит по `chat_id`; ник — по приглашению (оно заводит защищённый ключ), затем `key_unlock`. Убраны: токен чата
и вход по нему (`JoinArgs.Token`/`Key`, `Welcome.Key`, `ccqc token new`, `/quant-join <токен>`, `chat_join(token, name)`),
секреты ников, уровни протокола ниже 6, `nick reset`, `ccqc nick`, `nick-keys.json`, токены в `folders/*.json`.
Владелец входит под ником подписью `OwnerSig` каждый раз, без секрета; под защищённым ником не входит (`name_taken`).
Одноразовый мост на развёртывание превращал старую запись с токеном в `folders/*.json` в запись чата и стирал токен;
после развёртывания KEY-7 он удалён (`internal/local/bridge.go`, `Entry.Token`).
