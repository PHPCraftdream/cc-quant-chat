# Хранение: база узла и база на каждый чат

Решение владельца: у каждого чата своя база. Чат копируется, отдаётся другому узлу, удаляется и
чинится как один файл; порча одной базы не трогает остальные; блокировка и транзакции — на чат.

## Раскладка

```
<каталог данных>/node.db            узел: owner, origins, admin_log, настройки брокера, указатель чатов
<каталог данных>/chats/<chat_id>.db чат целиком: events + проекции + настройки чата + часы
```

Каталог данных: `CCQC_DB` (если он указывает на файл — каталог этого файла; сам файл не читается), иначе `<каталог конфигурации пользователя>/ccqc`. Файлы 0600, каталоги
0700. `ccqc db path` печатает каталог.

## Схемы и миграции

Два набора миграций: `migrations_node` (база узла) и `migrations_chat` (база чата). База чата мигрируется при открытии. Файл, смигрированный более
новым бинарником, не открывается: отказ только для этого чата (`store_unavailable`), остальные
работают.

База чата — одна строка `chat(chat_id, name, created_at, lamport)` и таблицы прежней схемы без
колонки `chat_id`: `nicks`, `rooms`, `room_members`, `messages`, `board_sprints`, `board_tasks`,
`board_workflow` (одна строка), `board_log`, `board_comments`, `docs`, `doc_versions`, `settings`
(только этого чата), `events`, `meta`.

База узла: `origins`, `owner`, `admin_log`, `settings` (уровня брокера), `chats` (chat_id, name,
file, created_at), `meta`.

## Открытие и закрытие

Чат открывается лениво при первом `Load`/операции и закрывается, когда брокер выгружает чат
(`Release`). Одно соединение на файл (запись одна). Указатель `chats` в node.db — для списка и
статуса; файл в `chats/`, которого нет в указателе, подхватывается при старте (имя берётся из
строки `chat` самого файла).

## Старая единая база (убрана в KEY-7)

Раньше брокер раскладывал единую `ccqc.db` по файлам чатов (`migrations_legacy`, `BackfillEvents`, отметки `layout`,
переименование в `ccqc.db.migrated`). Это убрано: старая база не читается, а `ccqc.db.migrated` — просто файл, который
можно удалить.

## Блокировки брокера

`Broker.mu` защищает только общее: карту чатов, соединения и счётчики остановки по простою; его держат
на мгновение и никогда — пока ждут чат. Операции участника внутри чата (`send`, `board`, `doc`, комнаты,
роли, чтение) идут под блокировкой чата `chat.mu`; чаты не ждут друг друга, в том числе когда store одного
из них медленный или завис. Чат, который нужно найти или загрузить (вход, сброс ника, админ-операция),
берётся через `useChat`: под `Broker.mu` только находят запись в карте (или кладут новую, уже
заблокированную «заготовку» на время загрузки) и берут на неё удержание (`refs`, чат с удержанием не
выгружается), затем `Broker.mu` отпускают и ждут `chat.mu` без него; если чат выгрузили, пока ждали
(`dead`), поиск повторяется. Если оба замка нужны сразу, `Broker.mu` взят первым, а замок чата только
пробуют (`TryLock`): так `ping`, janitor и выгрузка не встают за занятым чатом. Листовые мьютексы
(`hitsMu` — лимиты, `setMu` — настройки, `ownerMu` — ключ владельца, `ownerOpMu` — одна смена владельца
за раз) берутся на одно значение и ничего больше не захватывают. Ответ на запрос отправляется под
блокировкой чата, до порождённых им событий; `join` держит замок чата до отправки ответа. Вход в чат с
зависшей записью ждёт этот чат, остальное брокера не ждёт.
